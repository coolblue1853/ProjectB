# 모션 백서 — 이론·성공 조건·PixelLab 운용 (11-07 작성, 사용자 지시)

목적: 모션을 "프레임을 따로 맞추는 일"이 아니라 "한 몸이 이어서 움직이는 일"로 다룬다. 이 문서는 ① 우리 성공 조건 ② 외부 이론 ③ PixelLab 운용 규칙 ④ 판정 기준 ⑤ 연구 실험(생성 100회 예산)을 한곳에 둔다. 제작 절차는 `MotionPipeline.md`, 이펙트는 `MotionFxChecklist.md`.

## 1. 우리가 합격한 것의 공통 조건 (걷기·1타·2타)
기록 근거: `DungeonSlasherReference.md`(확정 레시피), `MotionPipeline.md` §6. 가설이 아니라 기록에서 뽑은 사실이다.
1. **방향이 안 바뀐다.** 걷기·찌르기·내려베기는 처음부터 끝까지 옆모습(east)이다. 몸이 도는 동작은 처음부터 안 맡겼다.
2. **첫 프레임이 하나다.** 기준 그림(ds03 대기)에서 전 프레임을 한 번의 호출로 만든다. 한 호출 안에서는 얼굴·몸 크기·옷이 유지된다.
3. **프레임이 짧다.** 공격 4장, 걷기·달리기도 반 주기 4장 ×2(첫·끝 고정). 8장 한 번 생성은 뒤 절반에서 몸이 3/4 정면으로 돌고 팔이 벌어졌다(걷기 6101~6103 실패).
4. **설명문에 방향 고정 문구.** "always faces right, never turns around or toward the camera", "same spot/size/facing, backpack attached".
5. **하체 변화가 작다.** 걷기·찌르기·내려베기는 발 위치 이동이 작고 서 있는 자세에서 낮은 자세로 가는 한 줄기 변화다.
6. **판정이 재생 단위다.** 걷기는 루프로 이어 봤고, 이음새 차이를 수치(≤ 이웃 평균 × 1.5)로 쟀다.

## 2. 올려베기 실패 원인 (11-06~07, 누적 20생성)
1. 프레임마다 **다른 방향 기준 그림**(② 3/4 앞 · ③ 옆 · ④ 3/4 뒤)에서 따로 생성 → 키·다리 간격·머리/배낭 크기·발 위치가 프레임마다 다름. 한 몸으로 안 읽힘.
2. 방향을 **한 번에 두 단계 이상** 건너뜀(앞 3/4 → 옆 → 뒤). 중간에 몸이 도는 과정(어깨 → 몸통)이 없었다.
3. 프레임을 **하나씩 보고 통과**시켰다. 이어 재생했을 때의 연속성을 판정 기준에 넣지 않았다.
4. 사이 프레임(광류 보간·PixelLab 사이 생성)을 얹어도 위 1·2가 그대로라 소용없었다.
5. 던파 레퍼런스의 자세는 맞췄지만 **칼 호(뒤 아래 → 앞 위)와 체중 이동(뒷발 → 앞발)** 이라는 올려베기의 본질을 규칙으로 두지 않았다.

## 3. 모션 이론 요약 (출처는 §7)
### 3.1 공격의 세 단계
- **예비(Anticipation) → 타격(Active) → 회복(Recovery).** 타격 판정은 엔진이 정하고, 그림은 이 셋이 읽히게 한다.
- 예비는 반응성 때문에 짧게(플레이어 공격 2~5프레임 @60fps, 중량 무기는 8~10). 회복도 짧게 — 길면 끈적인다.
- 무게는 프레임 수가 아니라 **유지 시간**으로 만든다: 예비·타격 자세를 길게, 사이는 빠르게(느리게 → 빠르게 → 느리게).

### 3.2 타이밍 수치(스프라이트용 시작값)
- 공격 6프레임 예: 100·50·50·50·100·50 ms(SLYNYRD 58). 5프레임 예: 예비 80 · 발사 50(스미어 가능) · 타격 유지 150~200.
- 걷기 4~6장·100~150ms, 달리기 6~8장·60~100ms, 대기 2~4장·300~500ms, 점프 정점 유지 120~180ms, 착지 눌림 80~120ms.
- 타격 직후 오버슈트: 회복 뒤 반대로 1px 이동 1프레임(빠를수록 크게). 히트스톱 평타 0.05초.

### 3.3 호(arc)와 몸
- 칼·점프·투사체는 **곡선 호**를 그린다. 직선이면 피스톤처럼 보인다. 호는 단순하고 일정하게(물결 금지).
- 큰 호(약 90° 이상, 머리 위 → 정면)는 느리지만 강하다. 좁은 호(찌르기·수평 베기)는 빠르다.
- 올려베기 = **낮은 예비(뒤 아래) → 몸이 솟으며 칼이 앞 위로 호** → 끝에서 몸이 가장 길게 펴짐 + 짧은 유지. 체중은 뒷발 → 앞발로 옮긴다.
- 스미어 프레임은 키 사이 1장, 빠르고 짧게. 호 위를 따라 간다(`MotionPipeline.md` §7).
- 팔·칼 끝을 최대 연장에서 살짝 길게(느슨한 느낌). 따라가는 부분(머리카락·코트)은 몸보다 1프레임 늦게.

### 3.4 스프라이트 기본 원칙(12원칙의 우리 적용)
- 포즈 대 포즈: 접촉·핵심 자세를 먼저 잡고 사이는 나중. 드리프트 방지.
- 픽셀 질량 일정: 프레임 간 몸·머리 크기 유지(6px 몸통은 6px). 양감 변화는 의도된 눌림(1~2px)만.
- 과장: 느끼는 것보다 약 30% 더. 작은 스프라이트는 미묘한 움직임이 사라진다.
- 실루엣 테스트: 검게 칠해도 무슨 동작인지 읽혀야 한다.
- 일정한 골격: 관절 길이 고정, 각도만 바꾼다(`skel_pose.py`).

### 3.5 방향 전환(턴어라운드)
- 표준 5뷰: 정면 · 3/4 앞 · 옆 · 3/4 뒤 · 뒤. **인접 뷰끼리만** 이어 간다(옆 → 3/4 뒤 → 뒤). 3/4 뒤가 옆 → 뒤의 사이 프레임이다.
- 모든 뷰에 같은 가로 기준선(머리·눈·어깨·허리·무릎·발)을 긋고 자세·크기·조명을 같게 한다 → 돌 때 커지거나 작아지지 않는다.
- 애니메이션 순서(3D 튜토리얼 기준): **머리 먼저 돌고 → 체중 이동 → 몸통 → 발 디딤 → 정지.** 머리 회전은 시작·끝에서 느리게.
- 좌우 대칭 소품은 반전으로 해결하고, 한쪽 소품(랜턴 등)은 뺀다(11-06 결정, 기준 8방향).

## 4. PixelLab 운용 규칙 (공식 문서 + 우리 기록)
1. **체이닝 생성:** 공식 워크플로는 "Freeze 1 → 2프레임 생성, Freeze 2 → 1프레임 추가"처럼 합격한 프레임을 고정 기준으로 이어 간다. 우리 MCP 에는 첫 프레임만 있으므로 **직전에 합격한 프레임 = 다음 호출의 첫 프레임 + 그 프레임의 골격**으로 이어 간다(서로 다른 방향 기준 그림에서 따로 시작하지 않는다).
2. **프레임은 적게:** 한 호출 3~4장. 문서도 "2프레임부터" 권장. 뒤 절반이 돌면 반 주기로 쪼갠다.
3. **첫 프레임 골격이 그림과 안 맞으면** 색·투명도가 조용히 나빠진다 → 골격은 기준 그림 위에 겹쳐 확인한다.
4. **하체 골격 고정:** 방향이 바뀌는 구간도 골반 높이·발 위치는 한 줄기 경로로 먼저 정하고 상체·팔만 바꾼다.
5. **머리 고정:** 머리가 많이 안 움직이면 머리 고정 옵션이 얼굴 일관성에 유리(공식 문서). MCP 에 없으면 설명문의 외형 고정 문구로 대체.
6. **시드는 실험 변수 외에는 고정**, 한 번에 변수 하나만 바꾼다. 같은 변수 2회 이상 반복 금지.
7. **칼·이펙트는 그림에서 뺀다**(`MotionPipeline.md` 원칙). 맨주먹 생성 후 코드로 붙인다.
8. **픽셀로 고칠 수 있는 건 PixelLab 에 돌리지 않는다**(크기·발 위치·잔 픽셀은 직접 수정).

## 5. 판정 기준 (고정, 프레임이 아니라 **이어 재생**으로 본다)
각 항목 0/1, 8점 만점. 합격 = 7점 이상 + ①②는 필수.
1. ① 한 몸으로 읽힌다(이어 재생 시 몸이 바뀌는 느낌 없음) — 필수
2. ② 호·체중 이동이 동작 이름과 맞다(올려베기는 낮은 예비 → 앞 위 호) — 필수
3. ③ 머리·몸통·배낭 크기가 프레임 간 일정하다(±1px)
4. ④ 발·하체가 튀지 않는다(경로가 연속)
5. ⑤ 얼굴·머리·소품이 유지된다(눈 뜸, 랜턴·무기 없음)
6. ⑥ 방향 전환이 있다면 인접 뷰 순서로 매끄럽다
7. ⑦ 레퍼런스 자세와 의도한 키 포즈가 맞다
8. ⑧ 실루엣으로 동작이 읽힌다
**판정 절차:** Claude 가 먼저 위 표로 점수를 매겨 `Docs/Playtest/MotionJudgeLog.md` 에 적고(사용자에게는 점수 없는 GIF 만 먼저), 사용자가 합격/불합격만 답하면 일치·불일치를 기록한다. 불일치 사유는 기준에 반영한다.

## 8. 검증된 레시피 — 올려베기 M1-a (11-07 사용자 합격, 이 순서를 다시 찾지 않는다)
결과물: `Docs/ArtCompare/CharacterGen/motion_research/m1_a_clean/f0~f4.png`(f0 = 입력 기준 그림). 원본 생성 `m1_a/`, 실험 기록 `Docs/Playtest/MotionJudgeLog.md`, 상세·정확한 문구 `Docs/ArtCompare/CharacterGen/motion_research/README.md`.
1. **생성 = 골격이 아니라 문장 방식 `animate_image_pixminimax`**, 4프레임(1생성), 첫 프레임 = 옆모습 기준 그림 `dir8_base/d3_side_r.png`(업로드 id 는 3일 만료 → 다시 `get_upload_url`), direction east · view side, seed 7001. 졸라맨 키는 쓰지 않는다(사용자 11-07 "졸라맨 방식은 안 될 것 같다").
2. **동작은 몸 동작과 호의 모양을 글로 쓴다**("웅크린 채 오른팔을 엉덩이 옆에 뒤로 빼고 → 온몸이 솟으며 팔이 아래 뒤에서 앞을 거쳐 머리 위로 → 뒷다리가 밀고 체중이 앞발로"). 모델이 스스로 몸을 돌려 등을 보이는 구성을 만들었고 사용자는 그것을 올려베기의 정상 동작으로 봤다.
3. **이펙트는 막을 수 없다.** 문구("no effects")·단어 제거로도 보장 안 됨(M1-b 는 동작이 약해 안 나왔을 뿐, M1-c 재발). 도움말 확인: 부정 프롬프트 없음. `inpaint_image` 는 한 장 10생성이라 쓰지 않는다.
4. **이펙트는 생성 뒤 직접 지운다(생성 0)** — `Tools/pixelfx/erase_fx.py` + 칸별 spec JSON(`motion_research/specs/m1_a_erase.json`). 색 자동 필터만으로는 머리카락(크림색)까지 지워지므로 **칸마다 지울 영역을 눈으로 정한다**. 호가 몸을 덮은 칸은 인접 칸의 같은 줄을 복사해 보충하고(`patch_from`) 모자란 픽셀을 칠한다(`paint`). 결과는 8배 확대로 확인.
5. 이어 재생(GIF)을 먼저 채점(§5)하고 사용자에게 보낸다. 점수는 사용자 판정 전에 로그에 적는다.
6. 남은 흠(다음 생성으로 고침): 마지막 칸 얼굴이 이전 칸과 다름 → 3번 칸을 첫 프레임으로 마지막만 1생성 체이닝.
**판정 기준 수정(11-07):** ⑥(방향 전환)은 "인접 뷰 순서"가 아니라 "재생했을 때 전환이 어색하지 않은가"로 본다. 등이 보이는 전환 자체는 올려베기에서 정상이다.
