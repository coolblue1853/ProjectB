## 2. 캡처 방법

### 2.1 전제
- 사용자 Unity 창을 앞으로 가져오지 않는다. 모든 호출은 `Tools/u.sh`(unity-mcp) 경유.
- **낮 시간대**로 바꾼다(`Tools/probes/set_day.cs`). 첫 호출이 장면 준비 전이면 안 바뀌므로 한 번 더 부른다(rig_check.sh가 그렇게 한다).
- 다른 세션이 C#을 고치는 중이면 플레이 캡처 금지(재컴파일로 NullReference가 난다. 동작 문제가 아님. MotionSpec39 §24 주의).
- 시작 전 세이브 백업(`AGENTS.md` 검증 1번): `%USERPROFILE%/AppData/LocalLow/DefaultCompany/ProjectB/*.es3` 복사. 끝나면 복원(md5 확인).

### 2.2 전체 모션 합본 캡처 (표준)
```
bash Tools/u.sh call read_console '{"action":"clear"}'
bash Tools/u.sh call manage_editor '{"action":"play"}'
sleep 15
bash Tools/u.sh cs Tools/probes/set_day.cs
bash Tools/u.sh cs Tools/probes/input_bg_on.cs
bash Tools/u.sh cs Tools/probes/state.cs               # playing=True 확인
bash Tools/u.sh cs Tools/probes/capture_all_motions.cs
# "scheduled N s, M motions" 가 나오면 N초 + 여유 기다린다
bash Tools/u.sh call manage_editor '{"action":"stop"}'  # 반드시 정지
bash Tools/u.sh cs Tools/probes/state.cs               # playing=False 확인
```
- 프로브가 하는 일: 동작마다 임시 도트 무기를 쥐여 셀 이름으로 재생. 배경·풀 렌더러는 끄고 캐릭터·이펙트만. 기본 3타는 v7 스미어를 같은 방식으로 띄운다.
- 카메라: 직교 크기 1.8, 단색 배경 `(0.15, 0.17, 0.21)`, 캐릭터를 반쯤 따라감(백스텝이 잘려서 10-30 수정), 해상도 360x240.
- fps: 1/30초 간격 **42장**(약 1.4초). 한 동작당 간격 1.6초.
- 결과 폴더: `Logs/playtest/all/<NN>_<동작>/f_000.png … f_041.png`.
- 일부만 다시 찍기: `Logs/capture_list.txt` 에 `동작,오른손무기,왼손무기` 줄을 쓰면 그 줄만 `Logs/playtest/sub/<HHmmss>/` 에 저장.
- 합본 영상: `python Tools/pixelfx/motion_reel.py Logs/playtest/reel.mp4` (30fps mp4, 자막).
- 오류 확인: `bash Tools/u.sh call read_console '{"action":"get","types":["error"],"count":"3","format":"plain"}'`.

### 2.3 3타 실제 휘두름 + 판정 시점 (인게임 숫자)
- 이펙트가 칼과 같은 시각인지: `Tools/probes/rig_strike_timing.cs` — 애니마다 실제로 고른 셀 이름과 이펙트 지연(초)을 낸다. "요청 셀 = 화면 셀"인지 확인(MotionSpec39 §24 18회차 버그가 이것이었다).
- 판정 시각: 먼저 `Tools/probes/to_spawner.cs`(몹 스포너 안으로 이동), 이어서 `Tools/probes/hit_timing_combo.cs`. 기준값: 공격 시작 → HP 감소 1타 0.26 · 2타 0.24 · 3타 0.26초(GameFeelPlan 10-28).
- 기본 이동 비교 촬영: `bash Tools/compare_moves.sh <태그>` → `Logs/playtest/cmp_<태그>_<walk|run|jump>.png`(0.04초 × 30컷). 기본 이동 점검 합본: `bash Tools/rig_check.sh` → `Logs/playtest/rig_check.png`.
- 스미어만 느리게 보기: `python Tools/pixelfx/smear_preview.py <폴더> 'base;full'` → board.png + 느린 GIF(0.25초/프레임).

## 3. 수치 검사 (도구와 통과 기준)

모두 생성 0, 프로젝트 루트에서 실행. 한글 출력이 깨지면 `PYTHONIOENCODING=utf-8`.

| 검사 | 명령 | 통과 기준 (기록된 값) |
|---|---|---|
| 보간 매끄러움·무기 끝 이동·멈춤 | `python Tools/motioncov/smoothness.py <셀...>` (인자 없으면 이동 셀 제외 전부) | 열: 장수·초·경로·최대·점프·멈춤·고르기. 큰 점프 = 한 프레임에 칼끝/손이 **18px 초과**. 멈춤 = 프레임 시간 **0.15초 초과**. `고르기` = 최대/평균 이동. 기준 3타 실측: 내려베기 점프 3·고르기 2.4, 올려베기 점프 4·고르기 2.4, 찌르기 점프 0·고르기 1.7. 도구는 **점프 2개 이상이거나 고르기 3.2 초과**면 "끊김"으로 표시한다. 기준 3타보다 나빠 보이면 불합격 후보 |
| 부위 크기(머리·몸) | `python Tools/pixelfx/part_check.py Idle,Stab,<셀...>` | 머리 면적·폭·높이 (기준 대기 `Idle (681, 32, 28)`). **±8%** 넘으면 `*` 표시. 사용자 규칙은 ±5% (memory body-consistency) |
| 프레임 흔들림·발바닥·키 | `python Tools/pixelfx/cel_check.py <프레임 폴더> [시작 끝]` | `bottom`(발바닥)은 걷기·달리기 0~1px, `h`(키)는 4px 넘게 변하면 커졌다 작아져 보임, `seam`(마지막→처음 diff)은 다른 프레임 평균보다 크게 튀면 루프 끊김 |
| 잡티·구멍·발바닥 높이 | `python Tools/pixelfx/cel_lint.py` | 잡티 0, 구멍 0, 땅 동작 발바닥 54행(공중·사망 제외) |
| 합성(셀+장비+칼+주먹) 도트 깨짐 | `python Tools/pixelfx/comp_lint.py ,iron_helm,iron_set Idle,Walk,Run` | dot / hole / edge / spike 모두 0에 가깝게 |
| 칼 각도·손 좌표 겹쳐 보기 | `python Tools/pixelfx/angle_audit.py <out.png> <클립,...>` | 빨간 점 = 손, 노란 선 = 게임이 붙일 칼 방향. 칼이 손에서 떨어지거나 방향이 몸과 안 맞으면 수정 |
| 구멍(리그 빈칸) | `python Tools/pixelfx/find_rig_holes.py` (`rig_holes_sheet.cs` 캡처 후) | 갇힌 자홍 픽셀 0 |
| 동작 구별도(비슷한 동작) | `python Tools/motioncov/similarity.py` | 가장 비슷한 동작까지 거리. 합치기 근거가 된 값: 0.19~0.22 무리가 "같은 몸". 새 동작이 기존과 이 범위로 붙으면 구별 재설계 |
| 졸라맨 단계 구별도 | `python Tools/motioncov/stick_similarity.py <keys json>...` | 위와 같은 기준, 키 json 단계에서 |
| 발 위치 추적(이동 비교 촬영) | `python Tools/pixelfx/track_feet.py <태그> <동작>` | 프레임별 뒷발·앞발 x·y, 발 간격 (아트 1px ≈ 화면 4.6px) |

### 3.1 도구가 없는 항목 (손으로 잰다)
- **몸통(머리 x) 뒤로 물러남**: 전용 도구 **없음**. 기록상 기준(MotionRootCause §4): 공격 중 머리 x는 공격 방향으로만, 뒤로 **3px 넘게** 빠지면 불합격(피격 제외). `cel_check.py`의 left/right 경계와 `cel.json` 손 좌표로 근사한다. 빌드 쪽 제한은 `build_cel.py` 의 `plan_x`(프레임당 3px, 대기 대비 -2~+6px).
- **팔다리 길이 변화(고무 팔)**: 전용 검사 **없음**. 생성 단계에서 `Tools/pixelfx/dir_keys.py`·`skel_pose.py` 가 고정 길이(허벅지 5.0·정강이 4.5·위팔 5.2·아래팔 5.0px)와 손목 0.97 이내로 강제한다. 결과 셀은 §4.1 시트에서 눈으로 본다.
- **손 위치 튐**: 전용 검사 **없음**. `smoothness.py`의 `max`(한 프레임 이동 중 손 이동 포함)와 `angle_audit.py`로 본다. 한 프레임에 18px 넘게 튀면 의심.
- **완급(유지 프레임)**: `smoothness.py` 의 `멈춤` 열 + `cel.json` 프레임 `time`. 기준: 준비 ≥ 타격 × 2, 타격 유지 0.03~0.18초 중 모션에 맞는 값(§6-3).
- **장비 레이어 ±5%**: 자동 도구 이름은 확인 안 됨(`build_equip.py` 의 `HELM_IOU`는 생성 쪽). 투구는 동작 확정 전까지 끈다.
- **타격 프레임 시점**: §2.3의 두 프로브(`rig_strike_timing.cs`, `hit_timing_combo.cs`).

## 4. 비교 시트 — 3타를 기준 줄로

### 4.1 형식 (GPT에게 실제로 보낸 형식)
- 각 장 **맨 위 줄에 기준 3타(Stab · SwingDown · SwingUp)**를 노란 이름표와 함께 둔다. 그 아래에 검토 대상을 한 줄에 동작 하나, 왼쪽 이름, 오른쪽으로 시간순.
- 대상 줄은 `Logs/playtest/all/<NN>_<동작>/f_###.png`에서 **0.1초 간격 10장**(3프레임 간격)으로 뽑는다. 기준 줄도 같은 간격으로.
- 3장씩 나눠 보낸다(GPT 이미지 한계). 회전 베기(`19 Spin`)도 사용자 합격본이라 기준 줄에 넣어도 된다(10-30 46동작 리뷰).
- 이 시트를 만드는 **전용 스크립트는 없다**. 기록상 대화 중 임시 PIL 스크립트로 만들었다(`Image.open` → 같은 크기로 `paste`, `malgun.ttf`로 이름표). 비슷한 합성 도구: `Tools/pixelfx/compare_sheet.py <out.png> REF=기준.png "A 설명=a.png" ... --scale 6 --cols 4` (캐릭터 도트 판정 지표 시트용. 모션 시트로 쓸 때는 지표 대신 이름표만 필요).
- 비교 영상: `python Tools/pixelfx/make_compare_video.py <이름> <태그1> <태그2>` (`cmp_<태그>_<동작>.png` 필요, 이동 비교용). 전체 모션 영상 `motion_reel.py`, 검토 영상 `motion38_review.py`(Docs/ArtCompare/Motion/m38_review/).

### 4.2 속도
- 정지 시트만으로 통과시키지 않는다(MotionRootCause §2). 실속도 영상 + **느린 영상(0.25초/프레임)** + 시트를 모두 본다.

## 5. GPT 채점

ChatGPT(Claude in Chrome의 ChatGPT 탭, 대화 "2D 공격 모션 설계")에 시트를 올리고 아래 프롬프트를 쓴다. 아래는 기록에서 찾은 **실제 프롬프트 그대로**다(대화 기록 10-29, 10-30). 이어서 같은 대화에서 보낸다.

### 5.1 품질 업 루프 — 1회차 (10-30)
> 최신 전체 동작이야(3장). 각 장 맨 위 노란 이름 3줄(Stab·SwingDown·SwingUp)이 사용자가 합격시킨 기본 3타 = 품질 기준이고, 그 아래가 나머지 동작(0.1초 간격 10장). 기준 3타와 비교해서, 기준보다 떨어지는 동작만 내림차순으로 표 하나: [번호_이름 | 기준보다 약한 점 1줄(키 자세 크기·예비동작·무게중심·실루엣·무기 궤적 중) | 키 자세를 어떻게 바꾸면 되는지 1줄(예: 장전에서 무기를 머리 뒤까지, 골반 3px 낮게, 타격 때 앞발 더 멀리) | 점수 10점]. 기준 수준(7점 이상)이면 빼줘. 가장 먼저 고칠 8개를 번호로 마지막에 적어줘.

### 5.2 재채점 (2회차 이후)
> 고친 뒤 2회차야(같은 형식, 맨 위 노란 3줄 = 기준 3타 7점). 바꾼 것: (고친 내용 한 줄씩). 아래 N개(…)는 아직 안 고침. 동작별 새 점수와 남은 문제 1줄만 표로, 그리고 아직 안 고친 N개는 키 자세 수정 지시를 구체적으로(손·발·골반 위치, 몸 기준).

3회차 이후는 더 짧게: "3회차(맨 위 노란 3줄 = 기준 7점). 바꾼 것: …. 동작별 새 점수 + 남은 문제 1줄 표로만."

### 5.3 전체 46동작 리뷰 (10-30 새벽)
> 이번엔 공용 동작 46개 전부야(3장, 한 줄 = 동작 하나, 왼쪽 이름, 시간순 7장). 무기는 확인용 임시 무기. 기본 3타(09 Stab·10 SwingDown·11 SwingUp)와 19 Spin(회전 베기)은 사용자 합격이라 기준이야. 엄격하게 보고: (1) 기준 대비 가장 약한 동작 8개를 순서대로(번호·이름·문제 한 줄·고치는 방법 한 줄 — 방향 프레임(E/SE/S/NE/N) 끼우기, 키 자세 깊게, 타이밍 중 무엇인지), (2) 서로 너무 비슷해 보이는 동작 쌍 3개, (3) 무기 각도·위치가 틀려 보이는 곳. 표로 짧게.

### 5.4 직업(외형 포함) 리뷰 (10-29 밤, 엄격한 아트 디렉터)
> 첨부 4장은 위 설계로 만든 직업 4개 시연 영상의 프레임(1/30초 캡처를 4장 간격, 왼→오, 위→아래)이야: 1) … 2) … 엄격한 아트 디렉터로서 직업마다 (a) 가장 어색한 프레임/구간 3개와 이유, (b) 무기 위치·방향이 틀린 곳, (c) 이펙트가 직업 정체성을 살리는지와 바꿀 점, (d) 상업 2D 액션(스컬·메이플·데드셀) 기준 점수 10점 만점을 표로. 듣기 좋은 말 말고 고칠 점 위주로.

외형 교체 후(10-30):
> 이번엔 외형까지 바꾼 직업 4개야(같은 몸 비율·같은 키 포즈로 외형만 교체): … 짧게 표 하나로: 직업별 점수(10점), 외형이 동작 중에 깨지거나 바뀌는 곳(모자·머리카락·후드 일관성), 무기·이펙트가 외형과 안 맞는 곳, 가장 먼저 고칠 1개.

### 5.5 규칙
- **통과 기준 7.0**(= 기준 3타). 6.9는 불합격.
- 점수가 올라도 **사용자 합격본이 우선**한다(회전 베기: GPT "몸이 덜 돈다" 지적에도 손대지 않음).
- GPT는 후한 경향이 있다(유사도 점수가 형태 실패를 못 잡은 사례, CharacterPixelRules §7). 형태는 시트를 직접 본다.
- 점수 항목: 키 자세 크기 · 예비동작 · 무게중심 · 실루엣 · 무기 궤적(5.1 프롬프트의 5개 축).
- **라운드 기록 방식**: `MotionSpec39.md` §24에 `N회차(날짜): 동작 이전점수→새점수(바꾼 내용 한 줄, 생성 횟수·누적)` 한 줄씩. 남은 지시(GPT가 준 수치 지시)는 같은 줄 끝에 적는다. 생성 0(타이밍·각도만)인지 재생성(PixelLab)인지 적는다.
- 같은 대화에 이어서 채점하고, 캡처 조건(카메라·간격)을 바꾸지 않는다. 바꾸면 점수 비교가 안 된다.
- 판정 도구가 맞는 셀을 보여줬는지 먼저 확인한다(§2.3).

## 6. 눈으로 보는 체크리스트

### 6.1 모션 (15항목) — 좋음 / 나쁨 / 근거

1. **키 포즈 3~5장만 봐도 무슨 공격인지 읽히는가.** 좋음: 준비·타격·마무리가 뚜렷. 나쁨: 균일 보간으로 키가 묻힘. (MotionSpec39 §1-2)
2. **완급이 있는가.** 좋음: 준비 길게 → 전환 빠르게(0.03) → 타격 유지 0.14~0.18. 나쁨: 모든 프레임 0.045초. (MotionRootCause #6)
3. **몸이 공격 방향으로 나아가는가.** 좋음: 찌르기에서 머리 앞으로(39 → 44). 나쁨: 뒤로 3px 넘게 빠짐. (MotionRootCause §4-10)
4. **칼이 지나간 뒤 끝까지 빠지는가("벰").** 좋음: 칼날이 손보다 앞서 지나감. 나쁨: 맞은 자리에서 멈춤("내려침"). (MotionPipeline §3)
5. **칼 든 손이 화면 오른쪽 손으로 고정인가.** 좋음: 끝까지 같은 손. 나쁨: 중간에 손 전환. (memory weapon-hand-rule)
6. **손 위치가 튀지 않는가, 손 크기가 같은가.** 좋음: 원을 그리며 이어짐. 나쁨: 프레임 사이 18px 점프. (smoothness, body-consistency)
7. **팔이 늘어나거나 꺾이지 않는가.** 좋음: 손목이 팔길이 0.97 이내. 나쁨: 고무 팔·골절. (Checklist §3)
8. **반대손이 몸통 기준으로 안정적인가.** 좋음: 배 앞에 거의 고정. 나쁨: 흔들거림·어깨 빠짐. (MotionPipeline §6)
9. **다리: 오다리가 없는가, 길이가 같은가.** 좋음: 뒷다리 곧은 사선, 앞 정강이 수직. 나쁨: 양 무릎 벌어짐. (MotionPipeline §3)
10. **몸이 큰가.** 좋음: 장전에서 머리·골반 3~4px 낮춤, 내려벨 때 주저앉음. 나쁨: 이펙트만 크고 몸 동작이 작음. (MotionSpec39 §20)
11. **머리 모양이 일정한가.** 좋음: 머리 폭·머리카락 ±5%. 나쁨: 출렁임·올려보는 얼굴. (body-consistency, 10-27)
12. **무기 끝 궤적이 이름과 맞는가.** 좋음: 내려베기 머리 위 → 앞 아래. 나쁨: 올려베기 장전에서 무기가 위로 섬. (MotionSpec39 §1-1, §22)
13. **콤보가 앞 타 끝 자세에서 이어지는가.** 좋음: 대기로 안 돌아감. 나쁨: 타마다 대기 복귀. (MotionRootCause #5)
14. **다른 동작과 구별되는가.** 좋음: 실루엣이 서로 다름. 나쁨: 시전↔양손 들기 같은 쌍. (MotionSpec39 §22, similarity.py)
15. **느린 재생에서 이름대로 읽히는가.** 좋음: 회전 베기가 실제로 돈다. 나쁨: "위로 두 번 휘적", "체조", "냥냥펀치". (사용자 10-29 판정)

### 6.2 이펙트 (10항목)

1. **칼끝에 붙어 있는가.** 좋음: 호가 칼끝 경로에 맞춘 원(반지름 = 칼끝 + 2px). 나쁨: 어깨 기준이라 칼과 떨어짐. (GameFeelPlan v6e/f)
2. **칼보다 먼저/늦게 나오지 않는가.** 좋음: 칼이 끝에 도착한 프레임에 등장. 나쁨: 고정 0.04초 지연. (rig_strike_timing)
3. **형태가 림버스 문법인가.** 좋음: 기울어진 타원 고리 + 머리 두껍고 꼬리 바늘, 찌르기는 바늘 쐐기. 나쁨: 원, 뭉툭한 굵기(반지름의 1/3). (LimbusReference)
4. **붓질로 보이지 않는가.** 좋음: 꽉 찬 호부터 시작해 가늘어짐. 나쁨: 머리가 그려 나가는 성장 프레임, 끝의 둥근 뭉치. (GameFeelPlan v6)
5. **찌르기가 발사체로 보이지 않는가.** 좋음: 칼에 붙은 잔상. 나쁨: 빛 창("미사일"). (10-28)
6. **색이 흰색 일색이 아닌가.** 좋음: 흰 날 끝 + 푸른 강철 몸 + 남색 안쪽(Steel 램프). 나쁨: 밝기만. (10-28)
7. **명암 3단인가.** 좋음: 흰 날·밝은 몸·안쪽 회색 띠. 나쁨: 2단의 둥근 덩어리. (MotionPipeline §7)
8. **몸·얼굴을 가리지 않는가.** 좋음: 시전 이펙트가 지팡이 끝 앞/발밑. 나쁨: 얼굴을 덮음, 수직 광선이 마법처럼 읽힘. (MotionSpec39 §20)
9. **짧고 꼬리부터 사라지는가.** 좋음: 2~5프레임, 36fps, 칼선 0.24초. 나쁨: 잔상이 오래 남음. (LimbusReference)
10. **초반 장비에 맞게 소박한가.** 좋음: 무채색·소형. 나쁨: 큰 실루엣·강한 글로우를 일반 무기에. (early-game-modest)

타격 이펙트는 추가로: 맞은 방향 쐐기/바늘 별, 둥근 섬광 금지(`Px_WHit7`, 64x48·4프레임 30fps).

## 7. 판정 결과 양식과 기록 위치

### 7.1 양식 (한 동작당)
```
동작: <번호_이름>   날짜: <MM-DD>   회차: N
캡처: Logs/playtest/all/<NN>_<동작>/ (조건: 낮, 42장 1/30초)
수치: smoothness 점프 n·고르기 x.x·멈춤 n / part_check 이상 없음|이상 / 머리 후퇴 n px
GPT 점수: x.x  (이전 x.x)   기준 7.0
눈 체크리스트: 통과 N/15 — 실패 항목 번호
판정: 합격 | 수정 필요
고칠 것: 프레임 번호 · 대상 · 수치  (예: F3 골반 3px 낮게, F5 칼 각도 -178° 표기, 타격 유지 0.14초)
방법: 생성 0(타이밍·각도·키) | 재생성(방향 프레임 / 측면 새 키, 생성 n회·누적 n)
```
- "합격"은 수치·눈 체크·GPT 7.0 세 가지가 모두 기준 이상일 때만. 하나라도 모자라면 "수정 필요".
- 사용자 합격본(기본 3타·회전 베기·기본 이동 셀)은 이 절차로 **수정하지 않는다**. 비교 기준으로만 쓴다.

### 7.2 기록 위치
- 라운드 기록: `.claude-rules/Game/MotionSpec39.md` §24 (한 줄씩).
- 새 교훈·실패 원인: `.claude-rules/Game/MotionFxLessons.md` §2.
- 이펙트 변경 이력: `.claude-rules/Game/GameFeelPlan.md` 해당 날짜 항목.
- 큰 흐름·결정: 해당 문서에 바로 적는다(대화는 압축되면 사라진다).
- 캡처 원본·GPT 시트는 `Logs/`·`Docs/ArtCompare/`(커밋 정책 확인). 스컬·림버스 그림이 든 비교판은 저장소 밖 `C:\Users\user\MotionRef\fx_compare`.
- 커밋 메시지에 검증 방법과 "미검증" 여부를 적는다. 캡처를 못 했으면 "미검증".
