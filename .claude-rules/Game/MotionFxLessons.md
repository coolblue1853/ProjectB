# 모션·이펙트 감각과 실패 교훈 (10-31 정리)

모션·이펙트·PixelLab 작업 전에 `MotionFxChecklist.md`(규칙)와 이 문서(감각·실패 교훈)를 **둘 다** 읽는다. 이 문서는 17~31일 사용자 피드백과 문서에 **기록된 것만** 모았다. 추측은 없다. 각 항목 끝의 괄호는 근거(날짜 또는 문서 절)다.

기준점은 하나다. **칼 3타(찌르기 v6·내려베기 v13·올려베기 v18) + 스미어 v7**. 새 작업은 이것과 나란히 놓고 같은 느낌이 나야 통과다.

## 1. 사용자가 좋다고 한 것

### 1.1 칼 3타 + 스미어 v7 (기준점)
- 사용자 평: 이펙트는 "정말로 마음에 든다", 림버스식 v7은 "진짜 한 100배는 나아진 것 같다", 3타 이펙트는 "수정할 거 없을 정도로 완벽"(10-28, 10-30).
- 보존 규칙: 태그 `keep/basic-motion-fx-v7`, 사본 `C:\Users\user\ProjectBKeep\basic-motion-fx-v7\`. 덮어쓰지 않고 새 이름으로 강화한다(10-28 memory `keep-basic-motion-fx`).
- 왜 좋았나 (기록된 이유):
  - 이펙트가 **칼끝 경로에 맞춘 원**에서 나왔다. 호 중심·반지름·시작/끝 각도를 칼끝에서 역산(`fit_tip_circle`, 반지름 = 칼끝 + 2px). 칼과 이펙트가 떨어지면 사용자가 바로 지적했다(10-28 v6e/v6f, GameFeelPlan).
  - 형태가 림버스 문법이다. 기울어진 타원 고리, 머리가 두껍고 꼬리가 바늘처럼 가늘어짐, 찌르기는 바늘 쐐기(LimbusReference).
  - 모션과 이펙트를 분리했다. 이펙트는 셀에 그려 넣지 않고 별도 레이어(10-27 memory `motion-batch-review`).
  - 동작 쪽은 졸라맨 3칸 GIF 승인 → 고정 길이 스켈레톤 보간 → PixelLab 1회였다(MotionPipeline §2, §6).
- 3타 인게임 실타격: 공격 시작 → HP 감소가 0.24~0.26초. 칼이 지나가는 시각과 맞음을 숫자로 확인(GameFeelPlan 10-28).

### 1.2 타이밍 F 곡선 (10-27 사용자 선택)
- 사용자: "1번(보간형) 괜찮아 보인다… 지금 타이밍이 선형이라 감·가속을 주면 느낌이 살 것". 결정은 F: 준비 50/40ms → 멈칫 70 → 가속 30/20 → 타격 유지 180 → 회복 45/60/90(MotionRootCause §13).
- 졸라맨 문서의 표현: 준비 유지 100ms → 베기 사이 30ms → 끝 자세 유지 150~180ms → 회복 50·60·90ms(MotionPipeline §3).

### 1.3 기본 이동·방향 판정 (합격 기록)
- 맨몸 걷기 셀 합격(10-26). 달리기는 "거의 완벽, 팔 움직임이 적다"(10-26). 점프 동작 자체는 "완벽"하지만 다소곳해서 다리 벌린 것으로 교체 진행(10-26).
- 대기: 허리에 손 올린 자세는 "메이플식이 아니다"라고 거절했고(10-26), 왼쪽 팔을 몸에서 살짝 **볼록한 곡선**으로 떼는 안을 골랐다(10-26 "저런 식이 아니라 곡선으로 해서 볼록하게 다시 들어오잖아").
- 직업 4개 최종본의 방향 프레임 혼합은 "방향 자체는 합격"(10-29). GPT 방향 혼합 판정은 MotionSpec39 §19.

### 1.4 회전 베기 (사용자 합격본)
- 닻 회전 = 회전 베기 셀은 "사용자 합격본이라 손대지 않는다". GPT가 "몸이 덜 돈다"고 해도 **사용자 합격이 GPT보다 우선**(MotionSpec39 §20, §24 14회차).
- 회전 구간은 0.04초로 빠르게 통과하고, 키(장전·타격)는 측면에서 0.10~0.15초 유지(MotionSpec39 §19).

### 1.5 이펙트 쪽 합격 요소
- 색: 흰색은 날 끝만, 몸은 푸른 강철색(`PixelRampId.Steel`: 흰 날 끝 → 하늘 → 푸른 몸 → 남색 안쪽). "너무 밝기만 하다"를 고친 결과(10-28).
- 칼 지나간 자리에 예리한 칼선이 0.24초 남았다가 꼬리부터 사라지게 한 것(10-28).
- 큰 동작(내려·올려베기)은 중간 프레임 한두 개 더(10-28 v6c). 올려베기는 살짝 더 넓게, 두께 8 → 11(10-28 v6b).

## 2. 사용자가 싫다고 한 것 — 증상 / 원인 / 고친 방법 / 다시 안 나게 하는 검사

### 2.1 고무 팔 (10-29 "무슨 팔이 고무인간이냐")
- 증상: 손이 몸에서 멀리 뻗고, 팔이 꺾이거나 늘어난다. "골절된 것 같다"(10-28, 칼든 팔).
- 원인: 손목 목표 좌표가 팔 두 마디 길이보다 멀어도 그대로 그렸다.
- 고친 방법: `dir_keys.py` 에서 손목·발목이 기준 두 마디 길이(2등신 팔 약 8px)를 넘으면 최대 거리로 줄이고 팔꿈치·무릎은 IK로 푼다. 관절 길이는 `skel_pose.py` 고정값(허벅지 5.0, 정강이 4.5, 위팔 5.2, 아래팔 5.0 px), 키 자세는 길이가 아닌 **각도**로만 적는다. 양손 무기는 먼 쪽 어깨를 몸 가운데로 비튼다(MotionSpec39 §18, MotionPipeline §1).
- 검사: 손목이 기준 팔길이의 **0.97 이내**(Checklist §3). 팔·다리 길이가 프레임 사이에 변하지 않는지 숫자로 잰다.

### 2.2 칼 든 손이 튀거나 바뀜 / 손 크기 변화 (10-27, 반복해서 화냄)
- 증상: 손 위치가 튀고, 손이 뭉개지고, 손 크기가 바뀐다. "여전히 내 말을 이해 못 하는 거야?"(10-27).
- 원인: 생성 초안마다 주먹·머리카락 크기가 달랐다. 칼을 그림 안에 넣어 생성기가 뒤쪽 팔로 들어 올렸다(memory `weapon-hand-rule`, `body-consistency-rule`).
- 고친 방법: 생성은 **맨주먹**("bare empty fists, holding nothing")으로 하고 칼은 코드로 손목에 붙인다. 투구는 빼고 기본 복장으로 작업한다(MotionPipeline §1, MotionRootCause §5).
- 규칙: 한손 무기는 화면 오른쪽 손이 주, 왼손이 보조, 동작 중 손 전환 금지(10-27). 비슷한 자세면 신체 부위 크기를 같게. 다리를 벌려도 원래 다리 길이를 넘으면 안 됨.
- 검사: 머리 폭·머리카락 덩어리·주먹 픽셀 수를 대기와 비교해 ±5%. 합성 시트로 손 전환이 없는지 확인.

### 2.3 몸이 뒤로 물러남 / 순간이동 (10-27 MotionRootCause)
- 증상: 찌르고 베는데 몸이 뒤로 빠진다. 피격에서 순간이동.
- 측정: 앞발 x 대기 47 → 찌르기 37(-10px). 머리 x 39.5 → 29.7~33.5. 피격 첫 프레임 머리 x 27.
- 원인: 생성기가 런지를 "앞발 고정, 뒷발 뒤로"로 그림. 프레임을 세로로만 정렬하고 가로는 그림 그대로 둠.
- 고친 방법: `build_cel plan_x` — 앞발을 대기 앞발 x 47에 고정, 머리 이동은 프레임당 3px, 대기 대비 -2~+6px로 제한, 콤보 2·3타는 앞 타 끝 머리 위치에서 시작, 피격은 머리 -3px. 결과: 찌르기 머리 39 → 44(앞으로).
- 검사: 공격 중 머리 x는 공격 방향으로만. 뒤로 3px 넘게 빠지면 불합격(피격 제외). 셀 안 골반 이동은 +5px 이내(MotionSpec39 §1-7).

### 2.4 투구 출렁임 / 투구가 머리와 따로 놂 / 다리 사라짐 (10-26, 10-27, 10-28)
- 증상: 달릴 때 투구가 머리와 따로 놀고 머리 도트가 깨짐. 투구를 쓰면 다리가 사라졌다 나타남(10-28).
- 원인: 장비 전이를 프레임마다 따로 그려 투구 모양이 매번 달랐다(투구 레이어 픽셀 수 공격 375~514, 대기 471).
- 고친 방법: 투구는 프레임마다 다시 그리지 않고 대기 투구 한 장을 머리 앵커에 옮겨 붙임(`HELM_IOU` 0.55 → 0.35, 결과 459~514 → 대부분 486~500). **장비 외형 레이어는 동작 확정 전까지 끈다**(맨몸으로 작업. 10-28 사용자 "투구는 나중에 해달라고 했다").
- 검사: 장비 레이어 픽셀 수가 대기 대비 ±5%.

### 2.5 균일 보간 / 허우적 / 국자로 뜨는 느낌 (10-27~29)
- 증상: "허우적대는 것 같다", "국자로 뜨는 것 같다", 올려치기에서 칼이 "날카롭게 올려치는 게 아니라 허우적"(10-27, 10-28). "보간 느낌이 안 산다"(10-29).
- 원인: 모든 프레임을 0.045초로 균일하게 두었다. 9~13장 균일 보간이 키 포즈를 묻었다. 머리 이동 2~13px로 키 포즈 자체가 작았다(MotionRootCause #6, MotionReferenceSurvey 진단).
- 고친 방법: 키 포즈 3~5장을 먼저 정하고 키 사이에 사이 프레임 1장씩. 유지 시간에 완급: 준비 길게, 전환 빠르게, 타격 유지. 준비 ≥ 타격 × 2(MotionSpec39 §1-2, MotionRootCause 기준 12).
- 검사: 프레임 시간 배열이 균일하지 않은가. 준비↔타격 사이 머리(골반) 이동 8px 이상(MotionSpec39 §1-3).

### 2.6 "벤다"가 아니라 "내려친다" / 붓질 (10-27, 10-28)
- 증상: "칼로 밴다기보다 내려친다", "붓으로 그림 그리는 느낌"(이펙트).
- 원인(동작): 칼이 맞은 자리에서 멈춤. 원인(이펙트): 머리가 그려 나가는 성장 프레임이 붓질로 보였다(GameFeelPlan v6).
- 고친 방법: 칼날이 손보다 앞서 지나가 끝까지 빠져나가게 하고 몸이 주저앉으며 숙이게. 이펙트는 **꽉 찬 호부터 바로 보인 뒤 가늘어지게**(`PICK`), 끝의 둥근 뭉치 제거(MotionPipeline §3, §7).

### 2.7 반대손(초록손) 이상 / 마지막에 자세 갑자기 바뀜 (10-27)
- 증상: 반대손이 흔들거리고 어깨가 빠진 듯함. 회복 때 자세가 갑자기 바뀜.
- 원인: 반대 어깨가 3/4 시점상 몸 앞쪽이라 팔을 가슴 앞/뒤 위로 올리면 꺾임. 반대손 각도가 월드 기준이라 몸을 숙이면 팔만 남아 흔들림. 회복 때 몸이 뒤로 미끄러짐.
- 고친 방법: 반대손을 몸통 기준으로 고정(`body_tuck`). 기본은 배 앞에 내리고(-85/-40) 동작 내내 거의 고정. 회복은 제자리에서 중간 자세(`IDLE_HERE`, `DOWN_MID`)를 거쳐 4프레임으로 풀기(MotionPipeline §3, §6).
- 검사: 칼팔만 보지 말고 프레임마다 머리·목·허리·반대손·두 다리를 전부 적어 레퍼런스와 비교(10-27 "몸 전체를 분석해야 잘 나온다, 잊지 말고").

### 2.8 오다리 (10-27)
- 증상: 내려칠 때 두 무릎이 양쪽으로 벌어짐. 올려칠 때 다리가 이상하고 멋없음.
- 고친 방법: 뒷다리는 뒤로 곧은 사선, 앞다리는 무릎이 앞을 향하고 정강이가 거의 수직. 오다리 금지(MotionPipeline §3).

### 2.9 칼이 너무 위로 / 얼굴이 이상해짐 (10-27)
- 올려치기 끝에서 칼이 너무 위로 올라가고, 올려보는 얼굴이 되어 얼굴이 이상해짐. 사용자 지시: 머리는 찌르기·내려치기와 같이 **정면을 본다**(10-27).
- 점프할 때 칼은 하늘 쪽으로 약 20도 더 올림(10-26).

### 2.10 거대 무기 / 뒤틀린 양손 무기 (10-29)
- 증상: 대검이 한 손에 매달려 머리 뒤로 눕는다. 납도 뒤 무기를 바꾸면 줄어든 소켓 배율로 새 무기가 거대해짐.
- 원인: 양손 무기도 주손 소켓 하나, 보조손 앵커 없음. 납도 칼 길이 채널의 소켓 배율이 남음.
- 고친 방법: 셀 데이터에 주손·보조손 좌표를 같이 기록하고 두 손 사이를 지나게 붙임. `AdoptWeapon` 에서 소켓 배율 초기화(MotionSpec39 §1-5, §24 5회차).
- 사용자 지시: 임시 무기는 우리 것이 아니라 새로 만들어 쓴다 ("지금 우리 무기가 이상하다", 10-29).

### 2.11 칼과 이펙트 범위가 안 맞음 (10-28)
- 증상: "칼 범위랑 이펙트 범위가 너무 안 맞는다", 내려베기에서 칼끝과 이펙트가 더 멀어짐.
- 원인: 호 중심을 어깨 기준으로 잡았다. 호의 시작·끝 각도를 칼끝 경로에 맞추지 않았다.
- 고친 방법: 칼끝 경로에 맞춘 원(`fit_tip_circle`), 원 중심에서 본 칼끝의 처음·끝 각도를 start·sweep에 넣음. 내려베기 -137° → 15.5°, 올려베기 49.7° → -148.9°.

### 2.12 이펙트가 동작보다 먼저 나옴 (10-28)
- 원인: 고정 `StrikeDelay` 0.04초. 새 3타는 준비가 0.16~0.19초.
- 고친 방법: 이펙트·판정을 실제로 재생되는 셀의 타격 프레임에 맞춘다(`StrikeFrameOf`, `WeaponFx.StrikeFrame`).

### 2.13 찌르기 "미사일" / 너무 둥글고 두꺼움 / 너무 부드러움 (10-28)
- `thrust_streak`는 머리가 뾰족한 빛 창이라 발사체로 보임. 베기가 둥글고 두꺼움. 3단 명암 대신 2단은 둥근 덩어리로 보임.
- 고친 방법: 찌르기는 칼에 붙은 잔상(스컬 Guard: 넓은 쐐기 1프레임 → 칼 따라 가는 선). swing_slash 두께 15 → 8, zigzag 12 → 6. 최종은 절차 생성 v7(§4).

### 2.14 연결이 끊긴 3타 / 밋밋한 리듬 (10-27 MotionRootCause)
- 증상: 3타가 따로 세 번 한다. 힘이 안 실린다(모든 프레임 0.045초).
- 고친 방법: 1·2타를 본편 + 회복으로 나눔. 다음 타는 앞 타의 끝 자세에서 시작(대기로 돌아가지 않음). 프레임별 시간 배열 도입(준비 0.05~0.08, 타격 0.03).

### 2.15 방향 프레임 무기 각도 표기 (10-30)
- 증상: 올려치기 장전에서 무기가 위로 선다.
- 원인: 각도를 182°·190°처럼 적으면 리그 `SmoothBlade` 가 -140° → 182° 를 위(90°)로 돌아 보간.
- 고친 방법: 직전 각도와 가까운 표기(-178°)로. 같은 방향의 각도 표기는 항상 직전 값과 짧은 쪽으로 이어지게(MotionSpec39 §22).

### 2.16 판정 도구가 틀렸던 사례 (10-30, 두 번)
- 대검 올려치기 점수 6.8~6.9는 사실 **양손 내려찍기 셀**을 보고 매긴 것이었다. `PixelRig.ApplyCel` 이 "Great…" 요청을 전부 GreatDown/GreatSide 셀로 덮어씀. 셀 이름으로 요청하면 같은 셀이 재생되는지 먼저 확인(MotionSpec39 §24 17·18회차).
- 다른 세션이 C#을 고치는 중에 플레이 모드 캡처를 하면 재컴파일로 NullReference가 난다. 동작 문제가 아니다. 캡처 직전 playing=False 확인(§24).
- 판정을 접촉 시트(정지 그림)로만 한 것이 근본 문제였다. 앞뒤 이동·리듬·이어짐은 숫자로 재야 보인다(MotionRootCause §2).

### 2.17 사용자가 거절한 동작들 (10-29 판정 기록)
- 교차베기가 주먹감자처럼 보임(a7). 회전베기가 위로 두 번 휘적(a10). 공중베기가 2번(a16). 주먹이 냥냥펀치(a18). 돌려차기가 체조/택견(r7, r11). 권총이 툭탁툭탁(a20). 견착이 너무 높음(a21). 검 든 채 사격하는데 칼을 찌름(a22). 올려치기가 끊겨 무겁지 않음(a25). 공중 아래 찌르기가 멈춰 있음.
- 공통 원인: 속도가 너무 빨라 읽히지 않음(a6 a23), 방패/무기 위치가 몸에 가려짐(a14 r8), 백스탭은 지형지물이 있고 실제로 뒤로 가는 모습이어야 보임(a17).
- 교훈: 동작은 느리게 돌려 읽히는지 먼저 본다. 이름과 실제 모양이 다르면 불합격(회전베기는 회전해야 한다).

### 2.18 재현 실패한 작업 방식 (10-25~10-27)
- 말로만 원본 재현(0·5·6세대): "최악, 같은 개념일 뿐"(CharacterPixelRules §7). 고정 체형 + 인페인트(4세대): "체형 고정은 오히려 안 좋았다".
- 생성 결과를 보고 고치는 순서가 거꾸로였다: 키 → 사이 → 문제 보이면 다시 생성. v5~v8은 키만 고쳐 바로 생성했고 사용자 판정 "똑같다·허우적"으로 PixelLab 낭비(MotionPipeline §6).
- 사용자에게 변형 여러 개를 고르게 함: "나한테 물어볼 것도 없이 하면 된다"(10-25). 한 장씩 판단을 떠넘기는 진행에도 크게 화냄(10-27). 둘 사이 균형은 §5.

## 3. 판단 감각 — 자세·완급·궤적·실루엣

### 3.1 키 포즈와 완급
- 키 포즈 3~5장을 먼저, 그것만 돌려도 무슨 공격인지 보여야 한다(Dead Cells 원칙, MotionReferenceSurvey 1).
- 완급은 비대칭. 가벼운 공격은 짧은 준비, 무거운 공격은 긴 준비·긴 회복. 균일 간격 금지.
- 시작값(60fps 기준, 측정치 아닌 시험값): 한손검 30/20/50(예비/타격/회복 %, 전체 0.27~0.40초), 양손검 45/15/40(0.50~0.80초), 둔기 내려찍기 45/10/45(0.55~0.90초), 단검 20/25/55, 창 30/15/55, 활 60/10/30, 총 25/10/65, 지팡이 55/10/35, 맨손 20/20/60(MotionReferenceSurvey).
- 림버스: 준비 자세 약 0.33초 유지 → 전환 2~3프레임 → 타격 자세 유지. 프레임 수는 적어도 유지 시간으로 맛을 낸다. 우리 준비 0.16~0.19초는 짧은 편(LimbusReference).
- 7점 통과 기록에서 실제로 먹힌 처방 (MotionSpec39 §24):
  - 소총 6.0 → 7.0: 조준 0.2초 버팀 → 발사 0.04 → 반동 → 천천히 복귀.
  - 백스텝 6.4 → 7.0: 웅크림 0.12 → 이탈 0.035×2 → 착지 웅크림 0.13.
  - 한손 수평 6.8 → 7.0: 장전 0.08 → 스냅 0.025 → 수평 타격 0.14 유지 → 짧은 팔로스루.
  - 채찍 6.5 → 7.0: 장전 0.12 → 스냅 0.04×2 → 최대 전개 0.12.
  - 던지기 6.1 → 7.0: 젖힘 0.12 → 릴리즈 0.03 급전환.
  - 당기기 6.4 → 7.0: 걸림 0.12 → 당김 0.06 → 젖힘 0.18.
  - 앞차기 6.8 → 7.0: 장전 0.14 버팀 → 뻗음 0.14 + 지지발 먼지.
  - 공통: **생성 없이 타이밍만 바꿔 올린 경우가 많다.** 재생성하기 전에 유지 시간부터 만진다.

### 3.2 무기 끝 궤적
- 분류는 이름이 아니라 **운동 방향 + 무기 끝 궤적**. 내려베기 머리 위 → 앞 아래, 수평 뒤 → 앞, 올려베기 아래 → 앞 위, 찌르기 몸 근처 → 정면 직선(MotionSpec39 §1-1).
- 무기 끝부터 정하고 몸이 따라온다. 몸 방향·무기 끝 방향·이펙트 방향이 같아야 한다. 손목이 아니라 무기 끝 궤적을 검증한다(§1-4, Survey 3).
- 준비에서 무기 끝은 몸 실루엣 밖(머리 위·등 뒤·발 아래), 타격에서 몸 밖 앞쪽까지(§1-3).

### 3.3 몸 움직임
- 베기 = 허리 비틀기, 찌르기 = 몸 전진, 내려찍기 = 상체 압축, 던지기 = 앞발 내딛기(§1-7).
- 내려벨 때는 주저앉으며 숙이고, 올려벨 때는 뒷다리를 펴며 솟는다. 다리 길이가 고정이라 골반은 최대 약 3px 내려가므로 머리 높이는 숙임으로 만든다(MotionPipeline §3).
- GPT 공통 지적: 이펙트 양에 비해 **몸 동작이 작다**. 장전에서 머리·골반을 3~4px 낮추고, 타격 직후 손을 가슴 앞에서 멈춘다(MotionSpec39 §20).

### 3.4 실루엣
- 내려·올려·수평·찌르기 실루엣이 서로 전혀 달라야 한다. 비슷한 쌍(양손 내려찍기↔올려치기, 양손 수평↔한손 수평, 시전↔양손 들기)은 불합격 신호다(§22).
- 양손 들기(정면 V): 손은 머리 양옆에. 머리 위에서 겹치면 팔이 사라진다(§19).
- 얼굴은 가려도 되지만 **팔이 꺾이면 안 된다**(§1-9).

### 3.5 보조손
- 양손 무기는 보조손 앵커 필수. 쌍권총은 오른총 반동 24°·왼총 22°로 교대(angleB 채널). 소총 견착 반동 16°.
- 반대손은 거의 고정이 기본. 올려치기에서 보조손도 자세를 잡다가 올려치는 쪽이 자연스럽다는 사용자 지적(10-27).

### 3.6 방향 프레임
- 회전·돌려차기·발도·납도·검+권총·양손 들기·던지기·방패 밀치기는 정면/뒷/3/4 프레임을 섞으면 확실히 좋아진다(GPT 판정 15개). 쌍권총·소총·모으기·시전·막기·채찍·백스텝·로프·앞차기는 측면 유지(§19).
- 로프: 우리는 뒷모습 유지(메이플식). 컨트롤러가 오를 때 로프를 플레이어 앞으로 올리던 것을 없앴다(§22). 로프 오르기가 "너무 길쭉해지는 느낌"이라는 사용자 지적(10-29).
- 뒷모습 프레임은 두 팔이 등 앞을 지날 때 배낭이 빠진다 → `paste_backpack.py`.
- 사용자 인식: "정면·뒷모습이 있으면 더 다양한 멋있는 자세가 가능하다, 그걸 먼저 했어야 했다"(10-29).

### 3.7 3타 대비 채점 기준
- GPT 점수 7.0 = 기준 3타 수준. 사용자 합격이 항상 우선(§4.4 회전 베기).
- 점수 흐름의 맛: 1회차 평균 4.5~6.5, 5~16회차를 거쳐 다수 7.0. 재채점은 반드시 **같은 캡처 조건**에서(§24).

## 4. 이펙트 감각

### 4.1 형태
- 베기: **기울어진 타원 고리**. 원이 아니다. 지름은 키의 1.5~2배. 머리(칼이 지금 있는 곳)가 가장 두껍고 지나온 길로 긴 꼬리가 바늘처럼. 두께는 반지름의 1/8~1/10(우리 v6은 1/3이라 뭉툭했다. LimbusReference).
- v7 수치: 꼬리 230°(내려)/220°(올려), 머리 두께 7/6px, 4프레임 36fps, 꼬리 비율 1 → 0.62 → 0.34 → 0.14.
- 찌르기: **바늘 쐐기**. 손 뒤 12px → 칼끝 너머 58px, 70% 지점 최대 두께 5px. 뒤에서부터 줄며 앞으로 나아감. 발사체(미사일)처럼 보이면 불합격.
- 타격: 맞은 방향으로 뻗는 **쐐기**, 불규칙한 바늘 별(4~8갈래, 길이가 서로 다름). **둥근 섬광 금지**. 크기 64x48, 4프레임 30fps(`Px_WHit7`). 스컬 소형 타격은 노랑·흰 4갈래 별 + 십자 점 2프레임.
- 스컬 문법 참고: 임팩트 1프레임 검은 실루엣 → 다음 프레임 흰 고리·방사선(반전 색 한 프레임이 "탁" 하는 맛). 베기 초승달은 약 0.1초(2~3프레임) 안에 사라지고 무기 그림보다 크다(SkulReference §4).

### 4.2 크기와 시간
- 이펙트는 2~4프레임, 꼬리부터 줄며 사라진다. 잔상이 오래 남지 않는다(림버스).
- 스미어 해상도는 셀과 같은 픽셀 크기(PPU 36 × 1.5 = 무기 24 PPU)와 셀 원점 피벗(MotionPipeline §7-4).
- 칼선은 0.24초 남았다가 꼬리부터 사라짐. 바람 호는 0.10초에 사라짐.
- 히트스톱: 평타 0.05초, 마무리 타 0.08초.

### 4.3 색 램프
- 흰색은 날 끝만. 몸은 색을 가진다(기본 칼 = Steel 램프). 전부 흰색인 경우는 림버스에 없다. 흰 램프는 거의 단색이라 납작했다(10-28).
- 진행 쪽 가장자리에 포인트 색(료슈: 검은 먹 + 빨간 날, 이상: 반투명 회색 리본).
- 명암은 3단(흰 날 · 밝은 몸 · 안쪽 회색 띠). 2단은 둥근 덩어리로 보인다.
- 직업 색은 모양 그대로 램프만 바꾼다(`MotionFxRamp`).

### 4.4 만드는 방식
- 형태(쐐기·타원·바늘)는 **절차 생성 도트**(`gen_smear.py`, `gen_hit.py`, `gen_motion_fx.py`). PixelLab으로 이펙트를 직접 생성하지 않는다(v5의 `vfx_workbench` 부품도 v7에서 절차 생성이 이겼다. 직접 그린 v1~v3은 품질 불합격).
- 세부는 셰이더·파티클 받침(`SmearAura`, 글로우는 호 안쪽 끔, 칼끝 불꽃 14개 접선 방향, 월드 공간). 도트일 필요는 크게 없다는 사용자 말: "도트로 큰 부분을 잡고 세세한 건 셰이더나 파티클로"(10-28).
- 순서: 레퍼런스(스컬·림버스) → 졸라맨 위에 면 계획 승인 → 부품/절차 → `fit_tip_circle` 로 칼끝에 맞춤 → **느린 미리보기(0.25초/프레임)** → 낮 인게임 1/30초 캡처.

### 4.5 초반은 소박하게
- 사용자 10-26: "초반 몹이라 너무 강대하거나 크게 보이면 안 된다. 장착 장비나 이펙트도 마찬가지. 힘을 준 건 유니크·레전더리". 기본 무기 이펙트는 무채색 소형. 화려함은 유니크·레전더리(memory `early-game-modest`).
- 유아틱 금지, 메이드 인 어비스 몽환·섬뜩(memory `abyss-mood-not-childish`).

### 4.6 하지 말 것
- 이펙트를 셀에 그려 넣기 / 모션에 이펙트를 섞어 만들기(재사용 불가).
- 호 중심을 어깨로 잡기. 대충 잡은 각도.
- 붓질(성장 프레임). 끝의 둥근 뭉치. 둥근 섬광. 발사체 같은 창.
- 흰색 일색. 몸·머리를 뿌옇게 만드는 글로우(호 안쪽 반지름 -8px은 끈다).
- 스컬/림버스 그림을 저장소에 커밋(한 번 `fx_plan_board.png` 에 스컬 프레임이 들어가 빼야 했다. 히스토리 06c4cfbd에 남음).

## 5. 작업 습관

### 5.1 보여주기 전 자체 검사 목록
사용자에게 보내기 전에 아래를 숫자로 끝낸다 (MotionRootCause §4 기준 + 사용자 규칙):
1. 머리 x가 공격 방향으로만 움직이는가(뒤로 3px 넘게 빠지지 않음).
2. 머리 폭·머리카락·주먹 픽셀 수가 대기 대비 ±5%인가. 장비 레이어도 ±5%.
3. 손목·발목이 기준 팔길이 0.97 이내인가. 오다리가 없는가.
4. 칼 든 손이 바뀌지 않는가(오른쪽 손 고정). 반대손이 흔들리지 않는가.
5. 프레임 시간에 완급이 있는가(준비 ≥ 타격 × 2).
6. 콤보는 앞 타 끝 자세에서 시작하는가.
7. 판정 시점이 실제 셀의 타격 프레임과 같은가. 이펙트 호가 칼끝에 붙는가.
8. 이름과 요청 셀이 같은 그림으로 재생되는가(2.16).
9. 느린 속도(0.25초/프레임)와 실속도 모두 눈으로 봤는가.
10. 기준 3타를 같은 시트 맨 윗줄에 놓고 비교했는가.

### 5.2 진행 방식의 균형 (사용자 지시가 두 번 바뀜)
- 10-27 초: "자세 하나씩, 보여주기 전에 스컬 레퍼런스로 강화한 뒤 하나씩"(여러 개면 판단 어렵다). 이어서 "한 번에 하자. 대신 성공 기준을 아주 높게" → 지금은 **모션 단위로 혼자 끝까지(스컬 설계표 → 키 → 사이 프레임 → 자체 점검 → 게임 적용) 하고 전체를 마지막에 한 번 보여준다**(memory `motion-batch-review`, 10-27).
- 사용자에게 선택지를 던지지 않는다. 지표·시트로 판정해 가져온다(10-25). 질문은 `Docs/OpenQuestions.md` 에 임시 가정과 쌓는다.
- 보여줄 때는 이것만: 졸라맨 3칸 GIF(레퍼런스 | 지금 | 수정안), 칼 붙인 시트, 3타 기준 줄 포함 비교 시트.

### 5.3 레퍼런스 고르기
- 횡스크롤 게임(던파·메이플·스컬·데드셀·림버스) 우선. 몸 전체가 보여야 한다. 머이브리지 같은 비게임 자료는 사용자가 "이상한 것"이라며 뺐다(10-27).
- 이펙트 때문에 몸이 가려진 프레임은 쓸 수 없다(던파M은 이펙트 없는 프레임에서만 관절 읽기).
- 레퍼런스 그림은 저장소 밖(`MotionRef`, `SkulRef`, `LimbusRef`). 커밋 금지. 유튜브는 음소거·정지 상태에서 프레임만 뜬다(10-27 memory `no-youtube-autoplay`).
- 외형 작업은 사용자가 말하지 않아도 스컬 + 림버스에서 먼저 형태·타이밍·색 문법을 정리한 뒤 만든다. 그림을 그대로 옮기지 않는다(10-28).
- 동작 설계는 "림버스에 있는 동작을 만들어라"가 아니다: ① 대부분의 직업에 대응 가능한 동작을 추린다 ② 그 모션에 필요한 정보를 림버스·스컬에서 추린다 ③ 기존 방식으로 강화해서 만든다(10-29).

### 5.4 GPT 채점 프롬프트 요지 (MotionSpec39 §19~24)
- 역할: **엄격한 아트 디렉터**. 기준은 기본 3타(찌르기·내려베기·올려베기)와 회전 베기. 점수는 10점 만점, 7.0 = 기준 수준.
- 입력: 전체 캡처 + 맨 위 줄에 기준 3타를 넣은 비교 시트.
- 받는 것: 약한 동작 순위, 비슷한 쌍, **키 자세 수정 지시(숫자: px·초·각도)**, 점수. 처방은 생성 0(타이밍·각도) 우선으로 받는다.
- 주의: GPT는 후한 편이라(유사도 점수 68~70이 형태 실패를 못 잡음, CharacterPixelRules §7) 형태 판정은 시트 육안이 필요하다. 사용자 합격본은 GPT 점수가 낮아도 손대지 않는다.
- 외형(4직업) 리뷰 점수는 외형 교체 뒤 오름(블러드 헌터 6.5, 사령술사 7.0, 기계공학자 5.5, 암살자 6.5. §23).

### 5.5 캡처 방법
- 낮 시간대로 고정한 뒤 인게임 캡처(밤은 안 보임. memory `test-daytime`). `capture_all_motions.cs`, 3타는 `Logs/_combo_bare.cs`(1/30초), 스미어 인게임은 어두운 배경 60fps `Logs/_aura_cap.cs`, 타격 `Logs/_hit7_cap.cs`.
- 같은 조건 0.04초 × 30장 스트립을 원본과 후보 모두 찍고 `compare_moves.sh`, `track_feet.py`, `make_compare_video.py` 로 나란히 영상(10-26 memory `motion-quality-bar`: "프레임 단위로 제대로 봐봐").
- 캡처가 끝나면 **플레이를 반드시 정지**한다. 다른 세션이 C#을 고치는 중이면 캡처하지 않는다(2.16).
- Unity 창을 앞으로 가져오지 않는다(memory `no-focus-steal`).
- 이펙트 미리보기는 `smear_preview.py <폴더> 'base;full'` (board.png + 느린 GIF).

### 5.6 비용 습관
- PixelLab은 마지막에 **모션당 1회**(3생성). 확정 전 시안은 Pixen/Pixflux. 정리·색 줄이기·미러는 무료 workbench. 아끼는 순서 PixelLab > Claude > GPT(10-29).
- 재생성 전에 졸라맨·지표·타이밍으로 먼저 푼다. 재생성은 키가 틀렸다고 확신한 뒤.
- 맨몸 → 장비는 마지막. 모션이 확정된 뒤 방어구를 얹는다(10-27: 모션이 늘면 방어구 수만큼 추가 제작이라 모션 전체를 먼저 확정).
- 모션 총량은 39개 안팎으로 고정, 특수 형태는 변신형 셀로 따로(10-27, 10-29).

## 6. 다른 AI(Codex 등)에게 맡길 때

**모션·이펙트·스프라이트 제작은 Claude가 직접 한다. Codex는 코드·UI·데이터 연결만 한다.** 기록된 이유:
- 같은 품질을 내는 데 쓰인 판단(졸라맨 승인 → IK → 1회 생성 → 3타 대비 채점, 레퍼런스 읽기)은 대화 맥락과 사용자의 거절 이력에 의존한다. 사용자가 "다른 대화창에서도 같은 퀄리티가 나올까?"를 물었던 이유(10-30, 10-31).
- Codex 규칙(루트 `AGENTS.md`)에서도 PixelLab 등 유료 생성 도구는 금지다.

Codex에게 시켜도 되는 것:
- 이미 확정된 셀을 게임에 연결하는 코드(재생 프로파일, 타이밍 값 주입, `FxName`, 무기 프리팹 필드).
- 프로브·테스트 작성, 콘솔 에러 확인, 캡처 스크립트 실행(Claude가 판정).
- 데이터(CSV) 연결과 UI.

맡기지 않는 것 / 맡길 때 금지:
1. 새 모션 키 자세 작성, 졸라맨 판정, 스켈레톤 보간, PixelLab 호출.
2. 스미어·타격·모션 이펙트의 형태·색·크기 결정.
3. 3타(찌르기 v6·내려베기 v13·올려베기 v18), 스미어 v7, `Px_WHit7`, 기본 이동 셀 **덮어쓰기** (태그 `keep/basic-motion-fx-v7`).
4. 모션 합격/불합격 판정과 GPT 채점 해석.
5. 코드 연결 중에도 건드리지 말 것: 셀 PNG, `register.json`, `build_cel.py` 출력, 이펙트 스프라이트, `Docs/ArtCompare/`.
6. 모션·이펙트 지시가 오면 코드 연결만 하고 "Claude가 제작" 이라고 보고한다.
7. 코드 연결 뒤 확인할 숫자: 타격 프레임과 판정 시각이 같은가, 무기 소켓 배율이 초기화되는가(2.10), 셀 이름 요청이 같은 셀을 재생하는가(2.16).
