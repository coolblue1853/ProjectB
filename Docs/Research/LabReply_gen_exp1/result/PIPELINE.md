# 부위 교체(던파 아바타 · 메이플 장비 외형식) 제작 파이프라인 — PixelLab 비용·품질 기준 (11-10)

## 결론 먼저
1. **외형 슬롯 = 머리 · 갑옷(한 벌) · 장갑 · 신발 (+ 기본 코트 전용 배낭, 나중에 앞머리·뒷머리).** 근거는 `SLOT_DECISION.md`.
2. **세트는 항상 "한 벌을 한 번에" 입혀 생성**하고 공용 지도로 자른다. 부위별 단독 생성은 품질이 급감한다(실험 1, 사용자 확인).
3. **세트는 키 프레임만 생성하고 나머지는 원본 동작을 따라 옮긴다.** 21프레임 중 7장(33%)만 생성해도 옮긴 14장이 실제 생성과 실루엣 IoU 0.917(최저 0.875)이고, 눈으로 구분이 거의 안 된다(`study5/keyframes_tau02_warped.png`). 프레임 간 깜빡임도 전부 생성한 것과 같은 수준이다(0.158 vs 0.106~0.152).
4. **키는 생성 없이 미리 고른다**(`code/keyframe_select.py`, 원본 캐릭터 프레임만 필요). 대기 1장, 찌르기 1장, 내려베기 2장, 올려베기(뒷모습 포함) 3장처럼 동작 크기에 맞춰 자동으로 나온다.
5. 속옷 몸(맨몸 기반)은 **동작당 1번, 모든 프레임 생성**. 키만 생성하면 구멍이 6배로 늘어난다(64 → 400). 대신 모든 세트가 같이 쓰므로 세트 수와 무관한 고정비다.
6. 비용(세트 1벌, 고유 프레임 98장): 지금 방식 약 **75 gen** → 키 프레임 방식 약 **35 gen**(−53%). 아래 표.

## 1. 고유 프레임 수(비용의 분모)
`cel.json` 클립 62개는 그림을 돌려쓴다(Lunge·Throw·Bow… → `ds_stab`). **고유 프레임 98장, 고유 동작 22개**(`unique_frames.json`). 세트·속옷 몸은 이 98장만 만들면 62개 클립 전부에 적용된다.

## 2. 비용표 (단가: Transfer Outfit (Pro) 64px 1회 = 최대 15프레임 = 10 gen — PixelLab 공식 문서 확인. 기준 그림 ≈ 5 gen — 문서 기록 기준)
| 항목 | 지금 방식 | 권장 방식 | 근거 |
|---|---|---|---|
| 속옷 몸(동작 전체, 1번만) | 98장 = 7회 ≈ 75 | 같음(전부 생성) | 키만 하면 구멍 64 → 400 |
| 세트 1벌(4부위 동시) | 98장 = 7회 + 기준 ≈ 75 | 키 ≈ 33장 = 3회 + 기준 ≈ **35** | 키 33%로 실루엣 IoU 0.917 |
| 부위별 단독 생성(참고) | 부위마다 75 → 세트당 300 | 하지 않음 | 품질 급감 |

예) 세트 10벌(전부 새로 생성):
- 지금 방식: 속옷 75 + 10 × 75 = **825 gen**
- 키 프레임 방식: 속옷 75 + 10 × 35 = **425 gen**
- 키 비율 33%는 대기·찌르기·내려베기·올려베기 4동작에서 잰 값이다. 걷기·달리기처럼 다리가 크게 움직이는 동작은 키가 더 필요할 수 있다. **본 생성 전에 98장 원본으로 `keyframe_select.py`를 한 번 돌려 정확한 키 수를 확인한다**(생성 0, 수 분).

## 3. 세트 1벌 만드는 순서
1. 기준 그림 1장: 속옷 몸 `ds_idle_0`에 `edit_image_pro_flash`로 새 옷 **한 벌**(모자·장갑·신발 포함, **배낭·소품 없음**). 약 5 gen, 시안 2개면 10.
2. 키 목록: `python code/keyframe_select.py <원본 98장 폴더가 있는 패키지> keys.json 0.2` → `by_tau["0.2"].keys`.
3. `transfer_outfit`: 참조 = 1번 그림, 입력 = **키 프레임의 속옷 몸**(15장씩 묶어 약 3회), 시드 고정.
4. 나머지 프레임 채우기(생성 0): 각 비키 프레임은 같은 동작에서 proxy가 가장 작은 키의 세트 그림을 옮긴다(`study5_cost.warp_set`). 전용 CLI는 아직 없다(실험 A 결과를 보고 만든다).
5. 자르기·내보내기(생성 0): `python code/export_runtime.py map <세트 98장> regions <세트 id> <Equip 루트> --armor --cap-under under_fixed`
6. 검사(생성 0): `evaluate.py`·`study4_slots.py`와 같은 지표(구멍·노출·조각·머리 불일치)를 기존 세트와의 조합으로 돌려 기준 이하인지 확인.

## 4. 머리카락·헤어스타일 변경 대비(사용자 질문 11-10)
**지금 상태:** 머리카락은 속옷 몸(맨몸)에 붙어 있다. 헤어스타일이 하나라면 문제없다.

**헤어스타일 교체를 넣는다면:**
- **레이어 순서:** 속옷 몸(대머리) → **뒷머리** → 신발·갑옷 → 장갑 → **앞머리** → 모자. 긴 머리의 등 뒤 부분은 갑옷 밑, 어깨 앞으로 흘러내린 부분은 갑옷 위에 오도록 머리 한 벌을 두 레이어로 나눈다.
- **모자 × 헤어 조합 폭발 막기:** 모자가 "자기 윗선보다 위로 솟은 머리카락만 지운다"는 규칙을 쓰면 지울 마스크가 헤어스타일과 무관해진다(모자 수 + 헤어 수만큼만 에셋). 잎사귀 두건으로 잰 결과 정밀도 0.84 · 재현율 0.54(놓치는 건 두건 옆선 프레임당 약 4px). 반대로 "모자 둘레 n칸을 지움"은 보여야 할 머리까지 지워 정밀도 0.11로 실패. `gen_exp1_reply/hat_zone_vs_exact_erase.json`.
  - 긴 머리가 모자 밑으로 흘러내리는 것은 위 규칙에서 지워지지 않으므로 자연스럽게 남는다.
- **지금 머리가 가리고 있는 옷:** 프레임당 평균 7px, 뒷모습(`ds_up_3·4`) 31~32px(`gen_exp1_reply/hair_over_outfit.json`). 짧은 머리로 바꾸면 이 자리가 빈다. 옆·앞은 생성 0 보완으로 충분하고, 뒷모습은 대머리 속옷 몸 위에 세트를 입히면 원천적으로 생긴다.
- **필요한 생성:** 대머리 속옷 몸(동작당 1번, 약 75) + 헤어스타일마다 "대머리 속옷 몸 + 그 머리"(키 프레임 방식, 약 35). 헤어 레이어 = 둘의 차이. 앞/뒤 나누기는 대머리 몸 실루엣과 겹치는 쪽 = 앞머리, 몸 뒤로 나간 쪽 = 뒷머리(**미검증**).
- **옷은 여전히 머리카락 있는 상태로 생성한다.** 대머리 두상에 맞춘 모자는 머리숱(고글 위 2~5줄)만큼 작게 앉아 머리가 삐져나온다(`SLOT_DECISION.md`).
- **런타임:** 헤어 슬롯 2개(뒷머리는 갑옷 앞에, 앞머리는 모자 앞에 그림)만 C#에 추가하면 된다. 모자의 지울 마스크는 지금 `CelComposer`가 "레이어보다 먼저 아래 그림에서 지움"으로 처리하므로 그대로 쓴다.
